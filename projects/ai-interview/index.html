产品判断

面试是一场动态的、强上下文的对话

2024 年我在海外读本科，身边同学都在为求职面试发愁。我自己也一样——很多人不是没有项目经历，而是不知道怎么把经历讲成面试官听得懂、信得过的故事：写在简历上还行，一开口就逻辑乱、答不到点、被追问就露怯。

传统解法都不好用：找真人陪练，一小时几百块还约不到对口的；刷题库，问题是死的，不会顺着你的简历和上一句回答继续深挖。所以我判断这个赛道真正的空白不在"题多不多"，而在"能不能实时、动态、针对你"。我把这个想法带进朋友公司的智能体平台，成了首批孵化产品之一。

练习模式 · AI 考你

AI 扮演稳定的面试官，读你的简历和目标 JD，提问、听你语音回答、顺着回答追问，最后给结构化评分和改进建议。

实盘辅助 · AI 帮你

真实面试进行时，同时捕获你的麦克风和对方的系统音频，实时转写、判断哪句是面试官在提问，秒速给出回答思路。

两个模式共享同一套底座（简历/JD 理解、语音转写、LLM 编排、结构化输出）——不做两个产品，做一个能力底座上的两种交互。

核心架构判断

整个设计，是被「面试中那一秒」逼出来的

实盘辅助有一个残酷的延迟预算：面试官话音一落，留给我的窗口只有大约一秒。人正常对话的轮次间隔本就在两百毫秒量级，超过一秒对方就觉得你在卡壳；延迟大到几秒，不只是尴尬，是会直接暴露你在用工具。

所以我把整条链路切成冷、热两条路径——贵的、慢的、要联网的活全部前置到面试前，面试中只留最短的那条路。

冷路径

面试前 · 慢无所谓

能提前算的，全部提前算

解析简历 + JD → 判定技术领域 → 联网拉这个领域的术语表 → 排序截断 → 灌进语音识别当热词，同时备好结构化画像、可深挖项目、短板与评分标准。

热路径

面试中 · 每毫秒都算

不联网、不重新解析、不重读整段对话

转写 → 拼一个尽量短的 prompt → 流式吐答案。中间结果先渲染出来降低感知延迟，稳定结果再定稿。

这条线一立起来，后面每个设计都不是孤立功能，而是同一个原因的产物。

领域词表为什么必须前置——面试中现场联网查词等于自杀。为什么把关键状态抽成结构化字段——热路径要短。为什么「最近几轮留原文、更早的做摘要」——省 token 是次要的，主要是在抢首字延迟：输入越长，第一个字吐出来越慢。为什么要有「快答」按钮——给用户一个手动重触发，不必等系统判完静音。

「面试官话音一落，我只有大概一秒。」延迟，是这个产品的第一约束

冷路径 · 解析模块会联网

真正的活不是「拉词」，是排序和截断

解析模块读完简历 + JD 之后，会判断出这个人的技术领域，然后上网拉这个领域的术语表。这份表同时喂两处：灌进语音识别当热词（不做这件事，转写就会把 WebSocket、YOLO、RAG、FastAPI 换成音近的常见词，后面的追问和评分全建在错文本上）；以及供面试官 Agent 追问技术细节。

这一步让解析模块不只是「抽取器」——它会调用外部工具主动补充上下文，这正是「Agent」和「一段 Prompt」的分界。

但真实约束很硬：热词在建立语音连接时一次性传入、粒度是每场会话、不能中途改；临时词表有条数上限、单词不能含空格；而且塞多了反伤——通用词加太多会拉低专有词的识别率。所以真正的活是排序和截断：从简历、JD 和联网拉来的一堆词里，挑出「最可能在这场面试里出现、且最容易被转错」的那些。这是产品判断，不是工程搬砖。

热路径 · 以及那个桌面音频桥

桌面端不是将就，是唯一的正解

实盘辅助要同时听「你」和「面试官」。你的麦克风好办，浏览器能拿到。但面试官的声音是会议软件放出来的系统音频，浏览器采不到——网页的采集入口一个只给麦克风，另一个只能「分享某个标签页/屏幕」、系统音频还是「提示而非保证」且平台受限。要抓「扬声器正在播的声音」，必须走操作系统级接口，而那是浏览器沙箱够不到的。

所以解法是：一个极轻量的 Windows 桌面件专职采集，再用一个「房间号」把音频桥回网页端。这一笔我特别想讲——它证明我们看懂了这个硬约束，并且清楚产品主体该在网页，桌面端只做它非做不可的那一件事。而且「本机 / 对方」是两条物理声道，天然就是说话人身份，比事后做声纹分离更稳也更快。

Agent 怎么拆

考官和裁判，必须是两个角色

我没把它做成「一个 Prompt 包打天下的 chatbot」，而是拆成一个主流程编排 + 四个职责模块。但严格按今天的定义，四者分量并不相同——我如实区分，因为把状态层也叫成「Agent」是虚的，一戳就穿：

面试官 Agent真正的 Agent独立 prompt，在循环里跑：靠「上一轮回答」这个反馈决定下一步问什么。
评分 Agent真正的 Agent独立 prompt 与评分标准，刻意只给它干净上下文——只喂问题、回答和标准。
解析模块会用工具的工序一次性结构化抽取 + 联网拉领域术语表，因此够得上「会用工具的 Agent」。
复盘模块状态层，不是 Agent存每轮的输入、输出与评分，算跨轮次的变化。它是数据层，不该叫 Agent。

为什么提问和评价必须分开：让同一个 Agent 既当考官又当裁判，它会既温柔又没标准——主持对话的目标是「把天聊顺」，打分要的是「守住尺子」，两个目标融在一起，必然是前者赢、扣分被和稀泥。拆开之后，面试官可以咄咄逼人地追问，评分可以冷静客观地扣分。而且评分 Agent 故意不看那段「聊得很顺」的完整对话，它才不会被气氛带着走。

把资深面试官的直觉，写成规则

追问能力不是模型给的，是这几条给的

最早只让模型「扮演面试官」，它永远问那三句：介绍一下你的项目 / 你遇到过什么困难 / 你为什么适合这个岗位。太泛，没有任何训练价值。解法是在 Prompt 里把追问逻辑写成可执行规则：

每次只问一个主要问题
优先围绕用户刚才提到的具体内容追问
不要一次性列太多问题
回答太泛 → 追问细节
有技术点 → 追问实现方式
有业务结果 → 追问指标和验证方式
有明显不清楚处 → 追问边界和反思
配具体范例：提到 WebSocket 就追问「为什么不用普通 HTTP」

这件事让我第一次体会到：做 AI 产品，产品经理的核心工作之一，就是把「高手脑子里的隐性判断」显性化、结构化，喂给模型。

而多轮追问会让上下文膨胀——塞太多，模型反而抓不住重点、开始忘事，而且输入越长首字越慢，在实盘场景里是致命的。我的策略是分层保留 + 摘要，真正的落地物是我设计的那组会话状态字段——把「下一步问什么」「已经问过什么」从对话流里抽出来，变成结构化字段，模型每轮只需要看常驻画像 + 当前项目 + 最近几轮 + 这两个账本：

user_profile 简历结构化信息（常驻） target_jd 目标岗位 JD（常驻） interview_stage 当前环节 → 决定继续追问 / 换题 / 进反馈 question_history 已问过的问题 → 避免重复 answer_history 用户回答 follow_up_points 待追问的点 → 决定下一步问什么 scoring_rubric 评分维度与分档 final_feedback 最终反馈

评分与反馈

没有稳定的尺子，模型调得好不好你无从判断

早期让模型给回答打分，同一个回答问两次能差十几分——因为「好」这个字对模型太模糊。解法是上明确的评分标准：我设计的维度包括回答完整度、结构是否清晰（有无 STAR）、是否贴合 JD、是否体现个人贡献、技术细节是否可信、有无业务结果、能否解释 trade-off、有无反思与改进；再落成几个可量化分项（总分、逻辑、JD 匹配、技术深度、表达）。

分档也写死：90 分以上要有结构有细节有结果有反思；70–80 分内容完整但细节或指标不足；60 分以下泛泛而谈、缺少个人贡献。再加两条硬约束——强制模型先输出扣分理由、再给分数，以及全部走结构化 JSON 输出。因为用户真正要的不是「78 分」，是「为什么扣分、怎么改」。

这塑造了我一个至今没变的信念：做 AI 评估类产品，评估标准必须先于模型迭代存在。（这个信念在我后来做 AI 驾驶检测时又被印证了一次：没有评估集，任何调参都是玄学。）

「能给出可执行的反馈」是上下文设计的产物，不是措辞技巧。

很多 AI 工具的反馈是「你答得很好，但可以更具体」——这句话本身就违反了它自己的建议。我们要求反馈必须落到「你没说清自己在项目里的具体角色」「你没解释为什么选 WebSocket」「你的回答和 JD 里的能力要求没对上」。但关键在机制：反馈之所以能这么具体，是因为简历、JD 和这一轮回答同时在上下文里，模型才能做「应该有什么 vs 实际说了什么」的差集。缺了 JD 它说不出「和岗位没对上」，缺了简历它不知道你本来有什么可讲。

诚实的结果，与那一课

痛点强 ≠ 需求强 ≠ 付费意愿强

产品真上线了：能输入简历与 JD、能语音交互、能实时转写、能多轮追问、能给结构化反馈；支持面试/笔试/双栏模式、模型可选、触发可设、转写可纠错。但商业化没跑通——累计只有一位付费用户，流量也不高，产品后来下线了。没有用户量、留存、转化数据，这个赛道我们没跑到那一步，我不编。

事后复盘：不是技术不行，是我们对「需求强度」和「付费意愿」判断过于乐观。「求职焦虑」是真痛点，但它低频（只在面试前那几天焦虑，用完就走，订阅制天然错配）、信任门槛极高（把面试成败托付给一个工具，还有被发现的风险）、极度同质化（核心就是大模型 + 转写 + 悬浮窗，谁都能做）。三者叠加的结果是：这个品类极容易转化成注意力，极难转化成经常性收入。

所以真正的解法不是「再优化产品」，而是换买家、换场景——往「有人愿意报销、且高频复用」的方向迁移。这个赛道后来最出名的玩家，最终也正是靠离开面试场景才活下来的。这堂课我记到今天：痛点强、需求强、付费意愿强，三者之间隔着两条鸿沟，每条都得单独验证，而不是停在「这个痛点很真」就冲进去。这是我现在看任何 AI 产品机会时第一个会问的问题。

它是我用 Agent 的方式理解世界的起点。

当年很多设计是靠产品直觉摸出来的，但回头看，这些直觉踩中的恰恰是今天 AI Agent 领域最核心的问题：怎么切 Agent 的职责、怎么管上下文、怎么让输出可控、怎么把主观评价标准化、怎么在延迟约束下做架构取舍。所以这段经历的意义不是「我做了个成功产品」（它没成），而是它成了我 AI 产品认知的地基——后来我做 AI 驾驶检测全栈、深入 AI 辅助编程，都是在补齐和印证这里第一次撞见的那些问题。

一条我会主动讲清的边界：我在这个项目里做的是产品调研、需求定义、产品方案、技术选型论证，以及交互链路 / Prompt / 评分体系的设计与推动。后端框架是开发同学选定的，我不写后端代码。我主导并想清楚的，是这条链路怎么串、每个环节解决什么问题。
